# Infrastructure CI Validation

## Status

Implemented in the repository as credential-free GitHub Actions validation.

The repository now contains:

```text
Python quality workflow
infrastructure quality workflow
deterministic Lambda package validation
Lambda package reproducibility validation
application Terraform offline validation
state-bootstrap Terraform offline validation
immutable action references
Dependabot maintenance for GitHub Actions
static workflow contract tests
manual AWS identity-check workflow
reusable AWS identity workflow
```

The validation workflows validate repository behavior.

They do not:

```text
authenticate to AWS
create the Terraform state bucket
initialize a remote backend
run Terraform plan against AWS
run Terraform apply
publish Lambda deployment artifacts
deploy Lambda functions
configure GitHub branch protection
configure GitHub Environments
assume an AWS IAM role
```

A separate identity category exists in repository source:

```text
AWS Identity Check
Reusable AWS Identity
```

Those identity workflows are manually initiated identity proofs. They are not required pull-request validation checks. They do not run on pull requests or pushes. They do not deploy. End-to-end OIDC verification against AWS is not yet claimed.

## Purpose

CloudDoc has multiple build and infrastructure boundaries that must remain reproducible across developer machines and pull requests.

Before this workflow, the repository already provided local commands for:

```text
Python formatting
Python linting
Python tests
deterministic Lambda packaging
Lambda checksum verification
application Terraform validation
state-bootstrap Terraform validation
```

Only Python quality ran automatically in GitHub Actions.

This architecture adds a second CI boundary for packaging and infrastructure without mixing validation with deployment authorization. Identity verification is a third, separate boundary documented in [GitHub OIDC Trust Bootstrap](github-oidc-trust-bootstrap.md) and [ADR-026](../adr/ADR-026-separate-oidc-authentication-from-deployment-authorization.md).

```text
Manual workflow dispatch
        │

        ▼                                               ▼

        │                                               │
        ▼                               ┌───────────────┴───────────────┐
Format, lint, and test                  ▼                               ▼
        │                       Lambda package                  Terraform offline
        │                               │                               │
        ├── Python 3.12                 ├── Python 3.12                 ├── Python 3.12
        ├── development deps            ├── runtime deps                ├── Terraform 1.15.8
        ├── Ruff format                 ├── package build #1            ├── wrapper disabled
        ├── Ruff lint                   ├── checksum verification       ├── application root
        └── Pytest                      ├── clean outputs               │   ├── init -backend=false
                                        ├── package build #2            │   ├── fmt
                                        ├── checksum verification       │   ├── validate
                                        ├── compare SHA-256             │   └── Terraform tests
                                        └── no publication              │
                                                                        └── bootstrap root
                                                                            ├── init -backend=false
                                                                            ├── fmt
                                                                            ├── validate
                                                                            └── Terraform tests

Manual identity proof (not a required pull-request check):
AWS Identity Check
    → Reusable AWS Identity
    → GitHub OIDC token request
    → permissionless AWS role assumption
    → STS GetCallerIdentity
```

Validation remains credential-free. Identity proof is manually initiated and does not deploy.

The infrastructure jobs run independently.

The Terraform job starts from a clean checkout without the Lambda ZIP generated by the packaging job.

This preserves the contract that offline Terraform validation does not depend on a deployment artifact.

## Workflow Taxonomy

Validation workflows:

```text
Python Quality
Infrastructure Quality
```

Identity workflows:

```text
AWS Identity Check

```

Validation workflows remain `contents: read` only. Identity workflows receive `id-token: write` in addition to `contents: read`. Identity workflows are not required pull-request validation checks and do not run on pull requests or pushes.

## Workflow Triggers

Both validation workflows run on:

```text
pull requests targeting main
pushes to main
manual workflow dispatch
```

They do not use:

```text
paths
paths-ignore
pull_request_target
workflow_run
```

### Why no path filters

CloudDoc has cross-cutting repository inputs.

Examples:

```text
Python source changes affect the Lambda package.
Runtime dependency changes affect the package.
Packaging changes affect Terraform artifact hashes.
Terraform changes affect infrastructure validation.
Workflow changes affect CI behavior.
```

Running all required checks on every pull request keeps branch-protection behavior predictable.

A path filter can cause a required check to remain absent or skipped for a pull request.

The project accepts the additional runner usage in exchange for stable merge gates.

## Workflow Concurrency

Both validation workflows use branch-scoped concurrency.

Conceptual configuration:

```yaml
concurrency:
  group: <workflow-name>-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

When a newer commit is pushed to the same branch, an obsolete run can be canceled.

This reduces wasted runner execution while ensuring the latest branch state is validated.

## Permissions Boundary

Both validation workflows declare:

```yaml
permissions:
  contents: read
```

They do not request:

```text
actions: write
checks: write
contents: write
deployments: write
id-token: write
issues: write
packages: write
pull-requests: write
security-events: write
```

The validation workflows only need to read repository contents.

They do not comment on pull requests, publish artifacts, push commits, or request cloud identity.

Identity workflows separately declare:

```yaml
permissions:
  contents: read
  id-token: write
```

`id-token: write` only allows requesting a GitHub OIDC token. It does not by itself grant AWS access. AWS trust and role policies decide whether federation succeeds. See [GitHub OIDC Trust Bootstrap](github-oidc-trust-bootstrap.md).

## Checkout Credential Boundary

Every checkout step declares:

```yaml
with:
  persist-credentials: false
```

The validation jobs do not need a Git credential after checkout.

This prevents the checkout action from retaining a repository credential in the local Git configuration.

## Lambda Package Job

Job name:

```text
Lambda package
```

Runtime:

```text
ubuntu-latest
Python 3.12
15-minute timeout
```

### Dependency installation

The job installs the project runtime dependencies:

```bash
python -m pip install --upgrade pip
python -m pip install -e .
```

It does not install the entire development dependency set.

The package builder uses:

```text
pyproject.toml
requirements/lambda.lock.txt
```

as cache inputs.

The Lambda runtime lock remains hash-pinned and platform-specific.

### Reproducibility workflow

The job executes:

```text
build and verify package
capture SHA-256
clean generated outputs
build and verify package again
capture SHA-256
compare both digests
```

Conceptual commands:

```bash
make lambda-package-check
first_digest=<generated checksum>

make lambda-clean

make lambda-package-check
second_digest=<generated checksum>
```

The job fails when:

```text
first_digest != second_digest
```

### What the package check validates

The package builder and Make target protect:

```text
Python 3.12 execution
locked runtime dependency input
hash verification
Linux x86_64 wheel selection
handler importability
lambda_handler presence
approved package contents
deterministic ZIP metadata
generated checksum correctness
```

### Generated artifact boundary

The job generates:

```text
artifacts/lambda/clouddoc-app.zip
artifacts/lambda/clouddoc-app.sha256
```

inside its temporary runner.

The workflow does not upload those files.

It does not use:

```text
actions/upload-artifact
GitHub Releases
Amazon S3
container registry
package registry
```

The generated package is validation evidence for that run, not a promoted deployment artifact.

Artifact publication requires a separate identity, retention, provenance, and deployment decision.

### No Lambda artifact dependency

The Terraform job runs on a different runner from the Lambda package job.

Real `plan` and `apply` remain protected by the guarded workflow's Lambda artifact verification.

## Action Supply-Chain Policy

Approved external actions:

```text
actions/checkout
actions/setup-python
hashicorp/setup-terraform
aws-actions/configure-aws-credentials
```

Every action is pinned to a full 40-character commit SHA.

Current approved references:

```text
actions/checkout
    SHA: 3d3c42e5aac5ba805825da76410c181273ba90b1
    release context: v7.0.1

actions/setup-python
    SHA: 5fda3b95a4ea91299a34e894583c3862153e4b97
    release context: v7.0.0

hashicorp/setup-terraform
    SHA: dfe3c3f87815947d99a8997f908cb6525fc44e9e
    release context: v4.0.1

aws-actions/configure-aws-credentials
    SHA: e6de054238d6b7531b4efff3b6587d9aade6a06c
    release context: v6.2.3
```

`aws-actions/configure-aws-credentials` is approved only for identity workflows. Validation workflows must not use it.

Each workflow line keeps the release version as a same-line comment.

Example:

```yaml
uses: actions/checkout@<full-commit-sha> # v7.0.1
```

### Why full SHAs

A release tag is readable but mutable.

A full commit SHA is an immutable execution reference.

The same-line release comment preserves human review context.

### Approved update procedure

An action update requires:

```text
Dependabot proposal
release review
publisher verification
change-log review
Node runtime compatibility review
permissions review
workflow contract test update
successful repository checks
human merge approval
```

Do not update an action SHA without updating its version comment and the static contract test.

## Branch Protection

Branch protection is a GitHub repository setting.

It is not configured by the workflow files.

After this slice is merged and the checks have run successfully on `main`, the repository owner should configure protection for `main`.

Recommended initial settings:

```text
require a pull request before merging
require status checks to pass before merging
require branches to be up to date before merging
require the three CloudDoc validation checks
block force pushes
block branch deletion
```

Recommended required checks:

```text
Python Quality / Format, lint, and test
Infrastructure Quality / Lambda package
Infrastructure Quality / Terraform offline
```

Possible later controls:

```text
required approvals
dismiss stale approvals
require conversation resolution
require signed commits
require linear history
administrator enforcement
rulesets
```

Those controls should be selected based on repository ownership and contribution model.

The project must not claim branch protection is active until it is configured and verified in GitHub.

## Security Considerations

Validation workflows:

```text
read-only workflow permissions
no persisted checkout credentials
no OIDC
no AWS credentials
no secret references
no artifact publication
no deployment commands
immutable action references
small approved action set
Dependabot update proposals
static supply-chain contract tests
```

Identity workflows separately request `id-token: write` and use the approved AWS credentials action only for permissionless identity proof. That boundary does not grant deployment authorization.

GitHub Actions remain third-party code executed by the repository.

Immutable SHAs reduce reference mutation risk but do not remove the need to review action source, publisher ownership, release notes, runtime changes, and permissions.

## Cost Considerations

GitHub-hosted runner consumption is the primary CI cost boundary.

Current design choices:

```text
one Python job
two infrastructure jobs
parallel infrastructure execution
15-minute infrastructure timeouts
10-minute Python timeout
```
